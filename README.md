# glm-ocr-service

Сервіс з веб-інтерфейсом: завантажуєш зображення в браузері — отримуєш
розпізнаний текст, готовий для копіювання. Під капотом — модель
[PaddleOCR-VL](https://ollama.com/AuditAid/PaddleOCR-VL-1.6-0.9B) через Ollama.

Основний сервіс (`ollama` + `ocr`) працює однаково на Raspberry Pi, Mac чи
будь-якому Linux-сервері — все запаковано в Docker, тож переносити на іншу
машину = скопіювати папку й запустити `docker compose up`. Опціональний
режим «точний лейаут» (`docparser`, дивись нижче) — виняток, він працює
тільки на x86_64.

## Що всередині

- **`ollama`** — офіційний образ Ollama, тримає модель і віддає інференс.
- **`ocr`** — FastAPI-сервіс, який:
  - на `GET /` віддає веб-сторінку — перетягни/встав/обери зображення,
    натисни «Розпізнати», скопіюй результат кнопкою;
  - на `POST /ocr` приймає файл зображення (той самий ендпоінт, яким
    користується веб-сторінка, — можна викликати і напряму зі скрипта);
  - зменшує зображення до ~1 мегапікселя (за замовчуванням), щоб уникнути
    зациклення моделі — PaddleOCR-VL, як і більшість подібних невеликих
    OCR-моделей, тренували на невеликих зображеннях, і завеликі фото/скани
    провокують нескінченне повторення тексту;
  - ставить параметри, що знижують ризик зациклення (`repeat_penalty`, `repeat_last_n`);
  - **і як останній рубіж захисту** — сам виявляє, коли модель усе ж почала
    повторювати той самий абзац по колу (це трапляється навіть при
    правильних параметрах, на нетипових зображеннях), і автоматично обрізає
    текст одразу після першого чистого входження, а не віддає сторінки повторів.
- **`docparser`** (опціонально, `--profile precise`, лише x86_64) — офіційний
  пайплайн PaddleOCR (`PaddleOCRVL.predict`) із реальним аналізом лейауту
  сторінки, а не одним промптом до VLM. Дивись розділ «Режим `precise`» нижче.

## Запуск

```bash
docker compose up -d --build
docker exec ocr ollama pull AuditAid/PaddleOCR-VL-1.6-0.9B:latest
```

Друга команда завантажує модель (~1.8 GB) всередину контейнера `ollama`
один раз; далі вона лишається у volume `ollama-data` між перезапусками.

Перевірка, що все готово:

```bash
curl http://localhost:8000/health
```

## Веб-інтерфейс

Відкрий у браузері `http://<адреса-машини>:8000/` (наприклад
`http://raspberrypi.local:8000/` чи `http://localhost:8000/`, якщо сервіс на
тій самій машині). Далі:

1. Перетягни файл, встав скріншот (Ctrl/Cmd+V) або натисни на область і обери файл.
2. Вибери режим: Текст / Таблиця / Фігура-схема / Документ (Markdown) /
   Документ (точний лейаут, лише x86).
3. Натисни «Розпізнати» — за кілька секунд з'явиться текст у полі знизу.
4. Натисни «Скопіювати».

Якщо в `docker-compose.yml` увімкнено `API_TOKEN`, на сторінці є поле для токена
(зберігається лише в браузері, у localStorage).

## Використання без браузера (API)

```bash
curl -X POST http://localhost:8000/ocr \
  -F "file=@/шлях/до/скріншота.png" \
  -F "mode=text"
```

Відповідь:

```json
{
  "text": "розпізнаний текст...",
  "mode": "text",
  "model": "AuditAid/PaddleOCR-VL-1.6-0.9B:latest",
  "seconds": 4.2,
  "filename": "скріншот.png"
}
```

### Параметри форми

| Поле | Значення | За замовчуванням |
|---|---|---|
| `file` | зображення (обов'язково) | — |
| `mode` | `text`, `table`, `figure`, `document`, `precise` | `text` |
| `output` | `json` або `text` (звичайний текст без обгортки) | `json` |
| `max_megapixels` | перевизначити ліміт зменшення для одного запиту | `1.0` |
| `max_predict` | максимум токенів у відповіді: 64–2048 | `2048` |

Файл обмежено 20 MB за замовчуванням, щоб один невдалий upload не вичерпав
пам'ять Raspberry Pi. За потреби змінюй `MAX_UPLOAD_BYTES` у середовищі
контейнера. Розгорнуте зображення також обмежене 20 MP до декодування
(`MAX_SOURCE_MEGAPIXELS`), тому фото з надвеликою роздільною здатністю
спочатку зменшуй на телефоні або комп'ютері.

#### Режим `document`

Замість чистого тексту повертає **Markdown**, що зберігає структуру
зображення: заголовки (`#`, `##`), списки, **жирний**/*курсив*, таблиці.
У веб-інтерфейсі результат одразу рендериться як документ (кнопка
«Сирий Markdown» перемикає назад на текст-джерело для копіювання).

Це не справжній аналіз лейауту з координатами (як робить офіційний
пайплайн `paddleocr doc_parser`) — модель за один прохід «вгадує»
структуру з вигляду тексту на зображенні. Для листів, статей і простих
сторінок працює добре; складні багатоколонкові макети чи точне
позиціювання елементів відтворюються приблизно. Якщо цього не досить —
дивись режим `precise` нижче.

#### Режим `precise` (офіційний `doc_parser`, лише x86_64)

Замість одного промпту до VLM викликає окремий сервіс `docparser`, який
запускає справжній пайплайн PaddleOCR: спочатку модель детекції лейауту
(`PP-DocLayoutV2`) знаходить на сторінці заголовки/параграфи/таблиці/зображення
з координатами, потім кожен елемент розпізнається окремо і збирається назад
у Markdown у порядку читання. Результат точніший за `document`, особливо на
складних макетах — але й повільніший (два послідовні пайплайни замість
одного проходу 0.9B-моделі).

**Чому окремий сервіс, а не просто інший режим у `ocr`:** пайплайн
використовує `paddlepaddle`, у якого **немає офіційного wheel під
ARM64/aarch64** — тобто під Raspberry Pi. Щоб не ламати основний сервіс на
Pi, `docparser` винесено в окремий контейнер за Compose-профілем `precise`,
який на Pi просто не збирається й не запускається:

```bash
# тільки на x86_64-машині (Mac/Linux-сервер, НЕ Raspberry Pi)
docker compose --profile precise up -d --build
```

Перший запит після старту буде повільним — контейнер завантажує моделі
пайплайну (кілька GB) у volume `docparser-paddlex`, і це відбувається один
раз. Завантаження йде по черзі через кілька дзеркал (AIStudio → ModelScope →
BOS); з-поза Китаю перші два зазвичай не резолвляться і воно падає на BOS,
що саме по собі може зайняти кілька хвилин — це нормально, не помилка,
просто чекай. `docker-compose.yml` вже прописує `DOCPARSER_HOST`, тож
`ocr`-сервіс підхопить `docparser` автоматично, щойно той підніметься —
нічого додатково налаштовувати не треба. Без запущеного `docparser` режим
`precise` просто поверне зрозумілу помилку замість зависання.

Поки триває перший (повільний) запит, можна стежити за прогресом:

```bash
docker logs -f glm-ocr-docparser
docker exec glm-ocr-docparser curl -s http://localhost:8001/health
```

(порт `docparser` навмисно не проброшено на хост — до нього звертається лише
`ocr`-сервіс усередині Docker-мережі, тож перевіряти `/health` треба зсередини
контейнера, як вище.)

Простий текстовий вивід (зручно для скриптів):

```bash
curl -X POST http://localhost:8000/ocr \
  -F "file=@invoice.png" \
  -F "output=text"
```

## Захист доступу

Якщо сервіс буде доступний ззовні локальної мережі, увімкни токен:
у `docker-compose.yml` розкоментуй `API_TOKEN` і задай значення, тоді
запити мають містити заголовок:

```bash
curl -X POST http://localhost:8000/ocr \
  -H "Authorization: Bearer твій-токен" \
  -F "file=@invoice.png"
```

Без заданого `API_TOKEN` авторизація не потрібна (типово для локальної мережі).

## Перенесення на іншу машину (Pi, Mac, сервер)

1. Постав Docker і Docker Compose (`curl -fsSL https://get.docker.com | sh` на Linux/Pi,
   Docker Desktop на Mac).
2. Скопіюй цю папку.
3. `docker compose up -d --build`, потім один раз
   `docker exec ocr ollama pull AuditAid/PaddleOCR-VL-1.6-0.9B:latest`.

На слабких платах (Pi 4/5) перший запит буде повільнішим — модель прогрівається.
Наступні запити швидші, бо ваги вже в пам'яті.

## Налаштування продуктивності

Змінні середовища в `docker-compose.yml`:

- `MAX_MEGAPIXELS` — ліміт зменшення зображення (менше = швидше, але гірша якість на дуже дрібному тексті).
- `NUM_CTX` / `NUM_PREDICT` — розмір контексту та максимум токенів відповіді. Для звичайного
  документа/скріншота 2048 токенів більш ніж достатньо; якщо відповідь виправдано довга
  (велика таблиця), піднімай обережно.
- `REPEAT_PENALTY` / `REPEAT_LAST_N` — захист від зациклення. `1.0` вимикає штраф за повторення
  (так рекомендує картка моделі для чистого бенчмарку), але на нетипових зображеннях це
  провокує нескінченне повторення одного фрагмента. `1.15` — компроміс, який зупиняє
  зациклення, майже не шкодячи якості. Якщо зациклення все ще трапляється — піднімай до `1.3`.
- `REQUEST_TIMEOUT` (секунди, за замовчуванням 480) — скільки максимум чекати на відповідь від
  Ollama, перш ніж сервіс поверне помилку замість тихого зависання. На слабкому чи навантаженому
  CPU (Docker Desktop на Mac, Raspberry Pi) повна відповідь на `NUM_PREDICT` токенів при
  10-12 tok/s може займати 3-4+ хвилини — таймаут навмисно з запасом. Якщо бачиш
  `Could not reach Ollama ...` одразу після кількох хвилин очікування — це якраз він спрацював;
  піднімай значення, якщо машина ще повільніша, або зменшуй `NUM_PREDICT`, якщо відповіді
  короткі й довге очікування небажане.
- `TEMPERATURE` — рідко треба чіпати.
- `DOCPARSER_HOST` / `DOCPARSER_TIMEOUT` — адреса сервісу `docparser` для режиму
  `precise` і таймаут очікування (за замовчуванням 900с — має покривати не лише
  сам пайплайн, а й повільне перше завантаження моделі, якщо швидкі дзеркала
  недоступні). Порожній `DOCPARSER_HOST` = режим `precise` вимкнено.
- `DOCPARSER_MAX_MEGAPIXELS` (за замовчуванням `4.0`) — ліміт зменшення для
  режиму `precise`. Вищий за `MAX_MEGAPIXELS`, бо тут детекція лейауту сама
  шукає елементи на сторінці й виграє від деталізації, а не ризикує
  зациклюванням, як однопрохідна VLM-генерація.

## Про зациклення (важливо)

Це не гіпотетична проблема — невеликі OCR-моделі на кшталт PaddleOCR-VL можуть
почати повторювати той самий фрагмент тексту на певних зображеннях (переважно
нетипових для OCR: скріншоти застосунків, вікна з кодом, складні композиції).
Це відтворюється навіть напряму через `ollama run` без жодних кастомних
параметрів, тобто це не щось, що можна повністю прибрати тюнінгом
`repeat_penalty` чи `temperature`.

Тому сервіс захищається на двох рівнях:

1. **Параметри семплінгу** (`REPEAT_PENALTY`, `REPEAT_LAST_N`) — знижують
   імовірність зациклення, але не гарантують його відсутність.
2. **Пост-обробка відповіді** — сервіс сам шукає у готовому тексті блок
   з 1-4 речень, який повторюється 3+ рази поспіль, і обрізає все після
   першого чистого входження. Це працює незалежно від того, чи спрацювали
   параметри семплінгу, і саме воно рятує від сторінок сміття в результаті.
   Не застосовується в режимі `table`, бо там повторювані рядки можуть
   бути легітимними даними.

Коли це трапляється, відповідь API міститиме `"truncated": true` і
пояснення в полі `warning`, а у веб-інтерфейсі статус підсвітиться червоним.
Текст при цьому не порожній — у ньому весь унікальний вміст документа,
просто без повторів.

## Типові проблеми

- **Розпізнавання "висить" довго (хвилини) і не завершується** — на слабкому чи
  навантаженому CPU (Docker Desktop на Mac, Raspberry Pi) навіть чесна відповідь
  без зациклення на кілька сотень токенів при 10-12 tok/s займає 1-3+ хвилини.
  Подивись `docker logs --tail 50 ocr` — якщо рахунок токенів (`n_gen`)
  постійно зростає, це або звичайна повільна генерація, або зациклення (див. вище) —
  у другому випадку сервіс сам це виявить і обрізає результат.
- **`prediction aborted, token repeat limit reached`** — Ollama сама впіймала
  зациклення й перервала генерацію раніше, ніж дійшла до нашого пост-процесингу.
  Це нормально, просто означає, що зациклення було особливо завзятим.
- **`Could not reach Ollama`** — контейнер `ollama` ще не піднявся або модель не підтягнута
  (`docker exec ocr ollama pull AuditAid/PaddleOCR-VL-1.6-0.9B:latest`).
- **Режим `precise` повертає `"Mode 'precise' requires the optional docparser service..."`** —
  сервіс `docparser` не запущено. Піднімай його окремо на x86_64-машині:
  `docker compose --profile precise up -d --build` (на Pi ця команда не спрацює
  й не повинна — `paddlepaddle` не підтримує ARM).
- **`Could not reach docparser`** — контейнер `docparser` ще збирається/стартує
  (перша збірка образу довга через `paddlepaddle`) або ще не готовий.
- **Перший запит у режимі `precise` падає з таймаутом/помилкою, хоча в
  `docker logs glm-ocr-docparser` видно, що завантаження й розпізнавання
  тривають** — саме перший запит якраз і тягне моделі пайплайну (кілька GB),
  а дзеркало за замовчуванням (AIStudio/ModelScope) часто не резолвиться
  поза Китаєм, тож завантаження падає на повільніший BOS і може зайняти
  кілька хвилин. `DOCPARSER_TIMEOUT=900` в `docker-compose.yml` це враховує;
  якщо однаково не вкладається — піднімай ще, або просто зачекай і повтори
  запит: модель кешується у volume `docparser-paddlex`, тож наступні запити
  вже не завантажують нічого і йдуть значно швидше.
- **Режим `precise` дуже повільний навіть на потужній машині** — це очікувано:
  два послідовні пайплайни (детекція лейауту + розпізнавання) на CPU без GPU.
  Для швидкого результату лишайся на `document`; `precise` — коли важлива
  точність структури більше, ніж швидкість.
